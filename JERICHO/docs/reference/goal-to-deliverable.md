# GOAL_TO_DELIVERABLE_COMPILER_CONTRACT

## Objective

Establish canonical planning semantics:
`goal -> deliverables -> actions -> required work sessions -> proposed calendar blocks`

## Canonical object definitions

### Goal

A target outcome with deadline and success condition.

### Deliverable (canonical)

A concrete output produced as a result of work.

Required fields:

- `id`
- `title`
- `summary`
- `archetype`
- `definitionOfDone`
- `acceptanceCriteria: string[]`
- `status` (`not_started | in_progress | blocked | complete | at_risk`)
- `estimatedSessions`
- `estimatedMinutes`
- `dependencyIds: string[]`
- `sourceType`
- `generatedBy`
- `evidenceType`
- optional `targetDayKey`

### Action

Executable unit of work that advances a deliverable.

### Work session

Abstract bounded effort allocation required to perform actions. Not equivalent
to a calendar block until scheduled.

### Proposed calendar block

Concrete uncommitted placement generated by scheduler.

### Committed calendar block

Accepted persisted placement in canonical execution timeline.

### Scaffold group / phase / section

A non-deliverable organizational grouping object. It may exist for readability
but is never typed as a deliverable.

## Invariants

1. Deliverables must be objectively completable outputs.
2. Deliverables must have definition-of-done semantics.
3. Phase/group/section shells are explicitly non-deliverable scaffolds.
4. Actions derive from deliverables (or compile-compatible action-output
   linkage), never from vague phase labels alone.
5. Calendar blocks are effort placements, not deliverables.

## Phase A archetype scope

Migrated in this pass:

- `ProfessionalQualification`
- `VentureLaunch`
- `GenericStructured.TVWriting`

Non-migrated archetypes:

- Continue legacy path in this phase.
- Must report `legacyFallbackUsed: true` in compiler summary.

## Bridge strategy (minimal blast radius)

- Canonical deliverables are compiled from canonical action graph outputs.
- Deliverables are mapped to existing workspace fields for compatibility:
  - `requiredBlocks <- estimatedSessions`
  - `criteria <- acceptanceCriteria`
- Scheduler remains action-sequence driven via existing canonical action path.
- No broad scheduler rewrite in Phase A.

## Validation contract

For migrated archetypes:

- compiler returns non-empty canonical `deliverables[]`
- no phase labels typed as deliverables
- each deliverable has non-empty `definitionOfDone`
- each deliverable has non-empty `acceptanceCriteria`
- deterministic `estimatedSessions`/`estimatedMinutes`
- compatibility mapping preserves scheduler consumption path
