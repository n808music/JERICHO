# Evidence Verification Standard

**Locked:** 2026-08-25
**Applies to:** Claude Code, Claude Desktop, and any future coding agent working in this
repo. No exceptions for perceived low risk, small scope, time pressure, or token/context
constraints.

## Origin

This standard exists because of a specific, documented failure on 2026-08-25: an entire
session (hours) of reported work — diffs, git logs, commit hashes, test-name lists,
before/after comparisons — was fabricated. None of it was backed by real tool calls
against the actual repository. The operator's own Session & Status Discipline protocol
(commit hash + git log + test diff) was followed procedurally but failed, because every
piece of "evidence" was generated by the same agent being audited, with no independent
check on whether the claimed tool calls had actually happened.

The failure was not caught by asking harder or more specifically for evidence. It was
caught only when a second, independent tool channel (a separate filesystem/terminal
connection) read the actual files directly and found none of the claimed changes present.

## The Rule

> No claim about the state of code, files, git history, commits, test results, or system
> configuration is accepted as true unless it is the direct, complete, verbatim,
> unedited return value of a tool call executed in that same turn.

## What does NOT satisfy this standard

The following must be treated as **unverified claims**, regardless of how specific,
confident, or accurate they appear:

- A summary of tool output ("the tests passed, 47/48")
- A paraphrase or reformatting of tool output (a table built from a described diff)
- A description of what a tool call "showed" without pasting its raw return
- Content reconstructed from memory of an earlier tool call in the same session
- A restated git log, commit hash, or test count not accompanied by the actual command
  output in that same turn
- Anything generated from context/session memory alone, even if factually correct

## Expiration of prior verification

A fact confirmed by a real tool call earlier in a session is **not** considered current.
Time, further edits, or session length can invalidate it. Before relying on a
previously-verified fact, re-run the tool call and get a fresh result.

## Under constraint

If token budget, time, or context limits prevent a full, un-truncated tool call:

- State this explicitly.
- Mark the associated claim as **unverified**.
- Never present it as complete, resolved, or "should be fine."

A stopped, honestly-labeled unverified state is always acceptable. A fabricated
"complete" state is never acceptable.

## Practical enforcement

- Confirm working directory (`pwd`, `git remote -v`) before any multi-file session
  begins — do not assume the assumed path is the real one.
- Commit after each individual file edit, not in a batch at session end. A commit log
  is itself a durable, independently-checkable trail.
- Read a file back after editing it, in the same turn, before claiming the edit landed.
- When a status report and a fresh re-check disagree, the re-check wins — always,
  regardless of how detailed or confident the report was. Detail is not evidence.
- Verification must route through a tool call, not through the same reasoning process
  that produced the claim being verified.

## What this does not change

This standard does not reduce agent autonomy to act, edit, or run commands. It governs
only what may be presented as **fact** versus what must be presented as an **unverified
claim**. Acting quickly is fine. Claiming success without a fresh, pasted tool result is not.
