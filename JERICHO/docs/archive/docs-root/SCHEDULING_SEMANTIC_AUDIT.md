# SCHEDULING_SEMANTIC_AUDIT

## Conclusion (Evidence-Based)

**Outcome 2 + Outcome 3 (mixed issue):**

- **Outcome 2:** Different object types were previously labeled with the same
  noun (`blocks`), creating semantic/UI ambiguity.
- **Outcome 3:** Structure-level proposal count/status was not cycle/goal scoped
  and could read mixed proposal arrays, while per-row counts came from
  deliverable effort metadata.

This was **not** a pure scheduler materialization bug. The main issue was
semantic collision + source/scoping ambiguity.

## Exact discrepancy requested by user

Case observed: `2 blocks proposed` in header vs `3 deliverables × 4 blocks`
rows.

Trace confirms these are different objects:

- Header count = proposed calendar placements.
- Row count = abstract required effort sessions (`requiredBlocks`) tied to each
  displayed group.

The previous UI wording used `blocks` for both, making them appear equivalent
when they are not.

## What changed

1. Canonical semantic helper added:

- `src/state/structureSchedulingSemantics.js`

2. Structure bindings switched to semantic helper and explicit labels:

- Proposal count now explicitly `proposed calendar blocks`.
- Row effort now explicitly `required work sessions`.
- Group title now `Plan Sections` (phase-like) or `Deliverable Outputs`
  (output-like).
- Schedule status semantics made explicit (`proposal_generated`, `committed`,
  `none`, `unknown`).

3. Scope hardening:

- Proposal counts/status are cycle/goal scoped in helper to reduce mixed-array
  drift.

## Remaining compatibility paths

- `getCanonicalProposedBlocks` still supports a fallback read from
  `suggestedBlocks` when canonical field is missing. This remains a 1.0.x
  adapter path.
- UI now distinguishes object types and source scope; fallback behavior is
  guarded by tests to prevent misleading counts.
