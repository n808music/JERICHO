# SCHEDULING_SEMANTICS_CONTRACT

## Canonical Definitions

### 1. Deliverable

A **deliverable** is a concrete output produced as a result of work. Examples:

- Passed AWS CCP certification exam
- Completed practice exam set
- Final notes packet
- Exam registration submitted

A deliverable is **not** a calendar block. A deliverable is **not** merely a
grouping label. A deliverable may require multiple actions and multiple work
sessions.

### 2. Action

An **action** is an executable unit of work performed to produce or advance a
deliverable.

### 3. Work session (required work session)

A **work session** is an abstract required effort unit for planning load. In
current code, this is represented by deliverable `requiredBlocks` values. A work
session is not automatically a calendar block unless scheduled.

### 4. Proposed calendar block

A **proposed calendar block** is a concrete, uncommitted calendar placement
generated by scheduling. Canonical source: `state.proposedBlocks` (with
compatibility adapter fallback documented in selectors).

### 5. Committed calendar block

A **committed calendar block** is a proposed placement that has been
accepted/applied and persisted to canonical execution/calendar state. In active
scoring/status logic, committed evidence is represented by canonical execution
events (`kind==='create'`) and materialized block state.

### 6. Section / Phase / Grouping label

A **section/phase/group** is a planning organization label. Examples include
generic auto-strategy names such as:

- Planning & setup
- Core production
- Verification & finalization

These are not automatically deliverables in PM-output terms. UI must not call
them deliverables unless they represent concrete outputs.

## Allowed equivalences

- Required work sessions may inform how many proposed calendar blocks are needed
  over time.
- Actions may map to one or more proposed calendar blocks.

## Forbidden equivalences

- Deliverable count != proposed calendar block count.
- Required work sessions != proposed calendar blocks.
- Phase/section labels != deliverable outputs.

## Count invariants

- Deliverable count counts deliverable outputs or explicitly-labeled plan
  sections, never calendar placements.
- Proposed calendar block count counts only canonical proposed placements within
  explicit scope.
- Committed count uses committed execution evidence, not proposal arrays.

## Mandatory invariants

### Invariant A

A deliverable count must count deliverables, not sessions, not actions, not
calendar placements.

### Invariant B

A proposed calendar block count must come from canonical proposed blocks (or
documented adapter), with explicit scope.

### Invariant C

No UI surface may use bare term `blocks` for two different object types without
qualification.

### Invariant D

If phase/group labels are displayed, they must not be mislabeled as
deliverables.

### Invariant E

If both abstract effort counts and scheduled placement counts are shown, labels
must distinguish them explicitly.

### Invariant F

`Schedule generated` semantics must map to deterministic state rules. Current
canonical rules:

- `proposal_generated`: scoped proposed calendar blocks > 0
- `committed`: no proposals but committed execution evidence exists
- `none`: neither proposals nor committed evidence
- `unknown`: error state (e.g., `lastPlanError`)

## UI label rules

- Proposed placements: `proposed calendar blocks`
- Abstract effort: `required work sessions`
- Group heading:
  - `Plan Sections` for phase-like grouped planning labels
  - `Deliverable Outputs` for concrete output-oriented items

Do not use unlabeled `blocks` in mixed semantic contexts.
