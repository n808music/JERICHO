# PLAN_QUALITY_3_CROSS_ARCHETYPE_BUILDER_STANDARD.md

## Purpose

Define a reusable builder standard for preserving domain payload as plans
compress from:

- goal
- deliverable
- action
- block

This document is for generation quality. It does not change the existing
admission doctrine or evaluator seam.

Core rule:

Jericho must preserve domain payload during compression, not just planning
shape.

---

## Systematic Gap

Jericho is now strong at preserving:

- sequence
- phase
- quality posture
- proof/review structure

Jericho is still weaker at preserving:

- domain object
- domain method
- domain output
- domain proof standard

So the real cross-archetype problem is not "not enough words." It is:

Jericho currently carries planning grammar better than work substance.

---

## Compression Contract

Every generated deliverable and block title should preserve four things in
compressed form:

1. **Object** What concrete thing is being worked on

2. **Operation** What is being done to it

3. **Output / Proof** What visible output, artifact, or proof standard is
   expected

4. **Context** What lane-specific frame makes the title domain-native

This becomes the canonical cross-archetype compression contract.

---

## Replacement Standard

The system currently over-compresses by keeping:

- phase
- quality

It should keep:

- object
- operation
- output/proof
- phase when needed

Canonical formula:

**object + operation + output/proof + bounded readability**

Not:

**phase + quality + generic stage language**

---

## Deliverable Title Standard

Deliverable titles should follow a bounded shape like:

**[domain object] + [operation/output] + [phase or quality modifier]**

Examples:

- SQL query fundamentals practice set
- podcast episode batch recording workflow
- customer outreach lead pipeline baseline
- marathon long-run endurance block
- brand launch visual identity package
- certification exam domain review set

Deliverables should remain meaningful when read alone.

---

## Block Title Standard

Block titles should follow a bounded shape like:

**[verb] + [specific object] + [bounded output or method]**

Examples:

- write JOIN and GROUP BY practice queries
- import and normalize retail CSV tables
- record draft episode 1 voice track
- revise brand identity moodboard options
- complete week 3 long-run pacing session
- send first 20 qualified outreach messages

Blocks must feel session-sized, not generic.

---

## Directive vs Deliverable vs Block

The translation contract should be:

- directive = full meaning
- deliverable = compressed meaning
- block = session-sized meaning

Not:

- directive = full meaning
- deliverable = generic phase
- block = generic action

This is the main compression failure to avoid.

---

## Archetype-Independent Builder Questions

Before a builder emits a title, it should be able to answer:

### Deliverables

- What concrete object exists in this lane?
- What transformation or output is expected?
- What makes this lane-specific instead of generic?
- What proof or quality standard matters?

### Blocks

- What exact work action is happening?
- On what exact object?
- Toward what visible output?
- In what bounded session-sized form?

If a generated title cannot answer those questions, it is too hollow.

---

## Archetype Payload Maps

Each archetype should define a compact payload map with:

1. core objects
2. core operations
3. core outputs
4. core proof standards

Builders should compose titles from that map instead of generic staged language.

### Skill Acquisition

- Objects: concepts, exercises, datasets, examples, drills
- Operations: learn, practice, solve, review, explain
- Outputs: notes, solved exercises, case study, mock answers
- Proof: timed performance, explanation fluency, portfolio artifact

### Venture Launch

- Objects: offer, customer profile, funnel, landing page, outreach list
- Operations: define, build, test, refine, validate
- Outputs: offer sheet, page, pipeline, feedback log
- Proof: live asset, validated outreach, early conversion signal

### Physical Training

- Objects: run, workout block, pacing plan, mobility routine, long run
- Operations: complete, progress, assess, recover, taper
- Outputs: weekly training block, benchmark result, endurance session
- Proof: completed sessions, benchmark times, distance tolerance

### Creative Production

- Objects: episode, track, script, cut, edit pass, release package
- Operations: draft, record, edit, sequence, finalize
- Outputs: draft, cut, master, release-ready asset
- Proof: completed piece, publishable quality, review pass

### Professional Qualification

- Objects: domain topics, question sets, exams, notes, case prompts
- Operations: study, solve, review, simulate, remediate
- Outputs: study set, mock exam, answer bank, review sheet
- Proof: score threshold, timed completion, error reduction

---

## Universal Anti-Patterns

Reject or rewrite titles dominated by generic stage language like:

- setup
- production
- finalization
- readiness
- artifact
- review
- project 1
- project 2
- project 3

These are only acceptable when attached to a concrete object.

Bad:

- core production
- readiness review
- proof artifact
- project 2 applying portfolio-quality

Better:

- record draft episode 2 interview segment
- solve timed SQL joins and aggregates set
- compile GitHub-ready dashboard case study package
- rehearse certification mock exam remediation review

---

## Universal Acceptance Test

For every lane, a blind reviewer should be able to infer:

1. the domain
2. the work object
3. the intended output
4. the difference between sibling branches

If not, the builder is still over-compressing.

---

## Product Rule

A good title should pass this test:

Could a user see this title alone and know what domain-specific work they are
doing, toward what output, and why it belongs to this goal?

If not, the title fails.

---

## Standardization Principle

Do not standardize by making every archetype sound the same.

Standardize by giving every archetype the same compression contract:

- preserve object
- preserve operation
- preserve output/proof
- preserve bounded readability

But let the actual vocabulary come from the lane.

This is the difference between:

- uniform structure
- uniform genericness

Jericho should preserve the first and reject the second.

---

## Operational Guidance For PQ3+

For future builder slices:

1. identify the lane payload map
2. identify current generic fallback titles
3. replace them with object-bearing builder outputs
4. verify visible lineage in deliverables and blocks
5. keep evaluator doctrine unchanged

The goal is:

more plans pass because generation is better, not because admission becomes
softer.

---

## Bottom Line

The systematic gap is:

Jericho still compresses plans primarily through phase language instead of
domain payload language.

The reusable fix across all archetypes is:

make every builder preserve:

- goal object
- domain operation
- expected output or proof
- bounded readability

That is the cross-archetype builder standard.
